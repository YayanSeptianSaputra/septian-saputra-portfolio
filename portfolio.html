01 · Platform

API Regression & Production Verification Platform

StafBook's backend shipped with no real test safety net — ~37 unit tests on an in-memory database, and a deploy pipeline with no test stage. Regressions were only ever caught by manual QA. Starting July 2026, I designed and built an automated regression platform to close that gap — everything below, in about two months.

1

Inventoried and prioritized 943 API endpoints

Read the backend source directly, then built a tiered regression suite (smoke → P0 → P1) covering the highest-risk paths first.

2

3-tier test-data architecture

Read-only, write-safe, and destructive tiers — so regression runs safely against a shared staging environment without corrupting data other tests or manual QA depend on.

3

Daily CI, zero-duplicate bug filing

Runs at 02:00 WIB via GitHub Actions; failures are automatically filed to Jira and de-duplicated — the same defect never reopens a stale ticket.

4

30+ candidate defects from code alone

Found by reading route handlers, validation rules, and policies before a single test ran — endpoints that always return 200 regardless of outcome, GET requests that mutate state.

5

Everything committed, traceable to a ticket

As of 2 Oct 2026 the repository holds 301 automated tests across 64 specs — 174 web end-to-end, 95 API regression, 32 production post-deploy — plus 42 Maestro mobile flows. Each ticket has a test-case document (31 documents, 239 documented test cases) that points to the spec which runs it; known-bad behaviour is pinned as expected-failure tests until the fix lands, and defects are logged with reproduction steps. 202 commits in about six weeks.

● PRODUCTION

Safety-gated verification, live on app.stafbook.com

Used to prove 6 feature releases directly on production: payroll prorata, PPh21 tax withholding, and attendance changes.

Payroll Prorate Calculation (Hari Kerja Tetap) — From Calendar Range to Actual Attendance

Closed the gap between what the requirement owner expected (prorate by days actually worked) and what the system did (prorate by calendar range, silently capping to full pay). PRD · Improvement · Draft · SBOOK-4692

Off-cycle Partial Run Payroll — Original Stays in Review, Copy Holds the Paid Staff

Reproduced the problem on staging first: running part of an off-cycle payroll pulled the whole cycle out of Review, a partial rollback left a replica that ignored new settings, and a second partial run orphaned the first invoice. Specified the fix as a split model — the Original keeps following the settings, each partial run spawns a Copy that carries the plan and invoice, and rollback merges staff back — anchored on one invariant: every staff appears exactly once across all cycles. The PRD ships with a live 4-staff simulation, mocks for eleven front-end fixes, backend decision flows, and the evidence table. Broke it into a parent ticket with BE and FE sub-tasks and surfaced a separate backend bug (rollback of all staff returning HTTP 500) on the way. Open decisions are listed in the document rather than hidden.
